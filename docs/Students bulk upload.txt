# ==================================================

# 4. PRODUCT OBJECTIVE

# ==================================================

A school administrator must be able to:

```text
1. Choose the academic placement.

2. Download the exact Backend-provided CSV template.

3. Fill student data.

4. Upload the CSV.

5. Wait for asynchronous validation.

6. See row-level validation errors when invalid.

7. Confirm the import only after the Backend declares it READY.

8. Wait for asynchronous provisioning.

9. See final created/failed results.

10. Select students/audience for credential generation.

11. Choose one of three credential modes.

12. Generate credentials asynchronously.

13. Download a secure credential CSV.

14. Use that CSV to distribute temporary credentials operationally.
```

The frontend must be an orchestration/UI layer over the Backend contract.

The Backend remains source of truth for:

```text
validation
capacity
tenant scope
seat limits
credential policy
eligibility
password policy
execution state
security
```

# 13. THREE REQUIRED CREDENTIAL MODES

# ==================================================

Frontend MUST support all three:

```text

shared_admin_provided
```

Human-readable behavior:

```text
unique_generated
=

for every selected student.

shared_temporary
=
Backend generates one temporary password
shared by all selected students.

shared_admin_provided
=
The school administrator chooses one temporary password
shared by all selected students.
```

All three are required.

Do not drop or merge modes.

# ==================================================

# 17. FRONTEND SECRET-HANDLING REQUIREMENTS

# ==================================================

`sharedPassword` is highly sensitive.

Do NOT:

```text
store it in localStorage
store it in sessionStorage
put it in URL/query parameters
put it in analytics
put it in telemetry
log it to console
send it to error-reporting metadata
persist it in a global store unnecessarily
echo it in normal API result UI
```

After successful submission, clear password inputs/state as soon as practical.

Use:

```text
autocomplete="new-password"
```

or the project-equivalent secure input behavior where appropriate.

A confirmation field is a frontend-only UX concern.

Do NOT send:

```text
confirmPassword
```

to the Backend unless the actual API contract explicitly requires it.

# 23. SCALE / UX EXPECTATION

# ==================================================

This flow is designed for schools with approximately:

```text
1000+ Students
```

Therefore avoid frontend designs that:

```text
render thousands of heavy row components unnecessarily
hold huge duplicated datasets in multiple stores
poll every row individually
send one HTTP create request per student
```

The Backend owns batch execution.

Frontend should work at Batch level and paginate/virtualize row error/result views where needed.
